# md-updates-docx

This skill performs a tag-based replacement of document sections. It reads structured blocks from the Markdown source and writes them into matching bookmarked areas in the DOCX file while applying academic typography and paragraph layout constraints.

**Core Implementation**: `capstone/manuscript/md_to_docx.py` — provides `parse_manuscript`, `apply_updates`, `apply_annotations`, `compute_docx_sha256`, `update_manuscript_meta`, `full_rebuild`, `save_tag_map`.

The thin CLI wrapper (`scripts/update_docx.py`) calls these functions.

## Tag-Based Replace Format (Legacy Syntax)

The Markdown source divides sections using HTML tag comments:

```markdown
<!-- TAG: ch1_bg_of_the_study -->
### Background of the Study
<!-- UPDATE:START -->
Your paragraph content here...
<!-- UPDATE:END -->
```

### Parsing Logic

1. **TAG markers** (`<!-- TAG: tag_name -->`) delimit sections
2. **UPDATE blocks** (`<!-- UPDATE:START -->` ... `<!-- UPDATE:END -->`) contain the new content to inject
3. **REMOVE blocks** (`<!-- REMOVE:START -->` ... `<!-- REMOVE:END -->`) specify text to delete from the section
4. The script locates the corresponding bookmark in the Word document (e.g. `tag_ch1_bg_of_the_study` at the heading paragraph), deletes all body paragraphs between it and the next section bookmark, and inserts the content found inside `UPDATE:START` / `UPDATE:END`

### Section Boundary Detection

Section boundaries are determined by the **NEXT `tag_` bookmark in document order** (not "any bookmarked heading"). This avoids the bug where stopping at any bookmarked heading caused sections to end immediately when all headings are bookmarked.

### Canonical Tag Order

The 17 mandatory sections (processed in this order for index stability):

1. `ch1_introduction` — Chapter 1 / Introduction
2. `ch1_bg_of_the_study` — Background of the Study
3. `ch1_conceptual_framework` — Conceptual Framework of the Study
4. `ch1_objectives` — Objectives of the Study
5. `ch1_scope_delimitations` — Scope and Limitation of the Study
6. `ch1_significance` — Importance of the Study
7. `ch2_methodology` — Chapter 2 / Methodology
8. `ch2_research_design` — Research Design
9. `ch2_software_model` — Software Development Model
10. `ch2_project_plan` — Project Plan
11. `ch2_project_assignment` — Project Assignments
12. `ch2_population_locale` — Population and Locale of the Study
13. `ch2_research_instruments` — Research Instruments (SUS + NASA-TLX)
14. `ch2_data_analysis` — Data Analysis (LIVE K-Means)
15. `references_list` — REFERENCES
16. `appendix_a_use_case` — APPENDIX A (Use Case Diagram)
17. `appendix_b_letter_conduct` — APPENDIX B (Letter to Conduct Study)

## HTML-Comment Annotation Syntax (New Surgical Format)

For review-gated surgical edits, the parser also supports explicit annotation blocks inside comments. These allow paragraph-level precision without full section replacement:

### `<updated>` — Replace specific paragraph

```markdown
<!-- <updated section="ch1_bg_of_the_study" para="1">Revised first paragraph content.</updated> -->
<!-- <updated section="ch1_bg_of_the_study" para="1">Revised first paragraph content.</updated> -->  (split-comment variant)
```

* `section`: tag name (e.g., `ch1_bg_of_the_study`)
* `para`: 1-based paragraph index within the section (excluding heading)
* Content between tags replaces that specific paragraph

### `<to-be-removed>` — Mark paragraph for deletion

```markdown
<!-- <to-be-removed section="ch1_bg_of_the_study" para="2" reason="Outdated statistic">Old paragraph text.</to-be-removed> -->
```

* `reason`: explanation for audit trail
* Content is matched for verification before deletion

### `<human-task>` — Flag for manual intervention

```markdown
<!-- <human-task type="diagram" status="pending">Create IPO diagram for Conceptual Framework</human-task> -->
```

* `type`: `diagram`, `table`, `figure`, `review`, `fact-check`, `rewrite`
* `status`: `pending`, `in-progress`, `done`, `blocked`
* **Diagrams are always human tasks** — never auto-generated by pipeline

### `<fact-check>` — Verify claims

```markdown
<!-- <fact-check claim="SUS score >68 indicates acceptable usability" status="verified">Per Brooke 1996</fact-check> -->
```

* `claim`: the statement being verified
* `status`: `unverified`, `verified`, `disputed`, `needs-source`

## Academic Formatting Constraints

When writing content into the DOCX, the following layout rules are **explicitly applied** at the run/paragraph level for reliability (styles alone are insufficient due to template corruption risks).

### 1. Normal Paragraphs (Body Text)

| Property | Value |
|----------|-------|
| Style | `Normal` |
| Font | Times New Roman, 12pt (run-level) |
| Alignment | Justified (`WD_ALIGN_PARAGRAPH.JUSTIFY`) |
| Line Spacing | Double (`line_spacing = 2.0`) |
| Space Before/After | `0 pt` / `0 pt` |
| First-line Indent | `0.5 inches` |
| Left Indent | `0 inches` |

### 2. References Paragraphs (Bibliography Entries)

| Property | Value |
|----------|-------|
| Style | `Normal` |
| Font | Times New Roman, 12pt (run-level) |
| Alignment | Justified (`WD_ALIGN_PARAGRAPH.JUSTIFY`) |
| Line Spacing | Double (`line_spacing = 2.0`) |
| Space Before/After | `0 pt` / `0 pt` |
| First-line Indent | `-0.5 inches` (hanging indent) |
| Left Indent | `0.5 inches` |

**Trigger**: `is_references=True` passed to `insert_section_content()` when `tag_name == 'references_list'`.

### 3. Heading Paragraphs

| Property | Value |
|----------|-------|
| Style | `Heading 1` – `Heading 4` (per `#` nesting level) |
| Font | Times New Roman (size inherits from style) |
| Page Breaks | **MANDATORY**: `paragraph_format.page_break_before = True` on all Chapter headings (`CHAPTER`), `REFERENCES`, and `APPENDIX` headings to preserve pagination boundaries without relying on blank paragraphs |

**Implementation**: Applied in `surgical_update()` (pipeline.py:368-372) and `rebuild_docx_from_md.py` (lines 403-408).

## Cleaning & Rebuild Operations

### Paragraph Sanitization

The `full_rebuild` path (`rebuild_docx_from_md.py`) performs additional cleanup before inserting content:

1. **Strip all `tag_` bookmarks** — removes corrupted/duplicate bookmarks
2. **Fix body text styled as headings** — detects long paragraphs (100+ chars) or known body-start patterns incorrectly styled as Heading, demotes to `Normal`
3. **Remove duplicate paragraphs** — exact text match deduplication (keeps first occurrence, skips short/empty paragraphs)

### Bookmark Management

* Bookmarks use sanitized names: `tag_` + `sanitize_bookmark(tag_name)` (non-alphanumeric → `_`)
* Created at the heading paragraph via XML insertion (`w:bookmarkStart` / `w:bookmarkEnd`)
* Each bookmark gets a unique ID derived from hash of name
* On rebuild, all old bookmarks stripped first, then clean ones added

## Usage

### Surgical Update (Default)

```bash
python capstone/manuscript/skills/md-updates-docx/scripts/update_docx.py \
  --md capstone/manuscript/SecureCAT_Ch1_Ch2_Manuscript.md \
  --docx capstone/output/SecureCAT_Ch1_Ch2_Manuscript[never_delete].docx \
  --template capstone/templates/BSIT\ Capstone\ Template.docx
```

Optional:
* `--update-tags tag1 tag2 ...` — only update specific tags (default: all)
* `--full-rebuild` — full rebuild from template (bypasses surgical update)

### Full Rebuild Mode

```bash
python capstone/manuscript/skills/md-updates-docx/scripts/update_docx.py \
  --md <md_path> --docx <docx_path> --template <template_path> \
  --full-rebuild
```

This:
1. Opens template DOCX
2. Calls `full_rebuild(template_path, tags, docx_path)` which rebuilds all sections from MD content
3. Adds clean bookmarks and page breaks

### Dry-Run / Review Mode

The core `md_to_docx.py` supports `--dry-run` / `--review` for previewing changes before applying (see script for flags).

## Pre-Flight Drift Check (Mandatory)

Before surgical update, the script **automatically verifies** the local DOCX matches the MD META tag:

```python
if 'docx-sha256' in meta:
    current_sha = compute_docx_sha256(docx_path)
    if current_sha != meta['docx-sha256']:
        print("⚠️  DRIFT DETECTED: DOCX SHA256 mismatch!")
        print("   Run docx-drift-check skill first to resolve.")
        return 1
```

**Always run `docx-drift-check` before `md-updates-docx`** — the pipeline enforces this ordering.
